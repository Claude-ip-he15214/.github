<p>脚本跑着跑着开始被要求验证，是最难一句话说清的问题。可能是调用节奏太密，可能是几条脚本共用一个出口，也可能是出口本身在前一天就被标记过。这篇按故障树的路子写：先按现象分级，再一层层往下岔，每一层给出可执行的查证动作，落到最后通常能收敛到两三个具体原因。文中提到的命令和参数都在 Linux 或 macOS 本地跑过，Windows 下用 WSL 也能对得上。</p>

<h2>一、先把「被识别」这个模糊描述拆成三种现象</h2>
<p>不同现象指向的节点完全不同，混在一起查只会越查越乱。第一种是请求成功率下降，返回 429 或 403，说明限流或拒绝发生在网关层；第二种是返回正常但内容变成了验证页面，说明校验发生在应用层；第三种是登录态被踢，需要重新走一遍确认流程，这通常和会话绑定有关。先把这三种分开统计，各占多少比例，后面才知道往哪个枝杈走。</p>

<h2>二、故障树第一层：问题在调用特征还是在出口特征</h2>
<h3>同一出口换不同节奏，看是否复现</h3>
<p>把调用间隔从 200 毫秒放宽到 2 秒，重跑一轮。如果异常消失，问题主要在节奏，出口只是被顺带牵连；如果异常照旧，说明节点在出口。这一步成本最低，优先做。</p>
<h3>同一节奏换不同出口，看是否复现</h3>
<p>保持节奏不变，把出口换成一条完全没跑过的新线，跑同样时长。如果新线上不复现，说明原出口已被标记；如果新线也复现，说明是脚本行为特征太显眼，比如固定的 User-Agent、固定的请求头顺序、固定的重试间隔。</p>

<h3>并发超载这一枝</h3>
<p>机房小机器跑十个并发看不出问题，是因为带宽富余；住宅线路上行通常窄得多，实测可用上行常在 10 到 50 Mbps 之间，并发一高就容易触发上游的流量整形。先把单条线的并发压到 3 以内试，稳定了再慢慢加，别一次加到位。</p>
<h3>出口被标记这一枝</h3>
<p>判断方法很土但有效：新买一条线，只跑一条最简单的请求，看是否直接返回验证页。如果新线干净，旧线就是被标记了。标记有时效，也可能长期存在，别指望等几天自动恢复，换线比等更省事。</p>

<h2>四、把每个脚本分到独立出口，具体怎么落</h2>
<p>一号一环境的做法，落地时最容易漏掉的是「脚本和出口的映射关系」这一步。建议在配置文件里给每个任务固定一个出口标识，而不是在启动参数里临时指定。这样即使中途重启，也不会出现同一个任务两次跑了不同出口的情况。</p>

<h3>映射表怎么存</h3>
<p>一个两百行的 YAML 就够，字段写任务名、出口编号、归属城市、启用时间。跑之前先做一次连通性检查，把出口实际 IP 打日志，和映射表对一遍，对不上就拒绝启动。这一个小检查能省掉大量「为什么这条任务总是失败」的排查时间。</p>
<h3>日志里至少要留三个字段</h3>
<p>时间戳、出口编号、出口实际 IP。只记 IP 不记编号，后面按任务复盘时对不上；只记编号不记 IP，服务商中途换了落点你也发现不了。三个都留，出问题能一眼看出是哪条线在闹。</p>

<h2>五、收敛之后还剩哪些容易忽略的遗留项</h2>
<p>第一，DNS 请求是否也走了同一条出口。有些脚本只给 HTTP 配了代理，DNS 仍然走本地，导致解析结果和出口地区不一致，这一项很容易被漏掉。第二，时区和语言头。出口在多伦多，系统时区却是另一个城市，两个信号打架，校验就容易找上来。第三，重试策略。失败后立刻重试是最常见的放大错误，建议改成指数退避，起步 5 秒，最多重试三次。</p>
<p>这几项都不贵，加起来半小时能改完，但经常是「改了还是不行」的关键。建议每次换完出口，都按这份清单过一遍再放量。</p>

<h2>常见问答</h2>
<h3>脚本跑得慢一点就不会被识别了吗？</h3>
<p>答：降速能解决一部分限流问题，但不是万能药。如果出口本身已经被标记，再慢也会返回验证页。正确顺序是先确认出口干净，再谈节奏，反过来做容易白折腾。</p>
<h3>一条线跑多个脚本，冲突一定发生吗？</h3>
<p>答：不一定，但风险随脚本数量上升。两个脚本都在低频读操作时，共用一条线问题不大；一旦其中一个进入登录或写操作，共用就会把另一个也拖进来。建议按任务类型分组，不要按机器分组。</p>
<h3>换线之后多久能看出效果？</h3>
<p>答：一般跑一轮完整任务就能看出大概。我的做法是新线先跑三十次同样的请求，统计失败率和验证页出现次数，和旧线同期数据对比。三十次内差异明显，基本可以下结论。</p>
<h3>出口编号和 IP 变了，配置要全改吗？</h3>
<p>答：不用。配置里绑的是出口编号，服务商换落点时只要更新映射表里的 IP 字段。这也是为什么建议绑编号而不是直接写死 IP，后面维护省很多事。</p>
